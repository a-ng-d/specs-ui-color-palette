# Feature — Gamut (wide-gamut color export)

- **Status**: Draft
- **Package(s) concerned**: `engine-ui-color-palette` (gamut-aware color serialization — not implemented yet), `ui-ui-color-palette` (Settings UI — not implemented yet), `api-ui-color-palette` (`generate-code` already takes `colorSpace`; a `gamut` param isn't implemented yet), local & cloud persistence (new field on `Base` — additive, not implemented yet)
- **UI module**: no new module — extends the existing `src/ui/modules/settings` "Color management" section (see [Settings](settings.md)), which today already holds Color space / Vision simulation / Algorithm version
- **Related spec**: [Settings](settings.md) (§ Color management section this adds a field to), [Export](export.md) (§ CSS/SCSS/LESS color-space sub-choice, which already includes a "P3" option — see Open questions), [Palette](../01-domain-model/palette.md) §1/§5 (`Base`, `SettingEvent`/`UPDATE_COLOR_SPACE`)
- **Ticket**: Notion — "Prendre en charge d'autres gamuts modernes" (`POR-433`). 5 story points. **Not Pro-gated** — confirmed by the requester, overriding the raw Notion `Pro` checkbox on the ticket (clarified 2026-08-05; that checkbox evidently tracks something other than plan-gating for this item). Notes (French, verbatim): *"Actuellement, seul le gamut sRGB est pris en charge lors de l'export des couleurs. L'objectif est d'indiquer explicitement le gamut cible (sRGB, Display P3, Rec. 2020) afin d'optimiser les valeurs de couleurs pour les écrans modernes. La compatibilité maximale reste assurée sur sRGB ; P3 et Rec. 2020 sont des extensions pour les écrans wide-gamut. Le gamut est un paramètre propre à chaque palette (inscrit dans les paramètres de la palette, non global). Par défaut : sRGB, car c'est le standard quasi-universel et le plus compatible."*
- **Design**: Figma — `UICP Screens` file, frame **"Gamut"** (node `4972:24618`) — the palette Settings panel, "Color management" section, showing a new **Gamut** dropdown (`sRGB` selected) positioned first in that section, immediately above the existing Color space (`OKLCH`) and Vision simulation (`None`) dropdowns. The fourth field visible in the same section, "Chroma velocity" (`Sinusoidal and hyperbolic`), is **not new and not related to this ticket** — confirmed via Tolgee (`settings.color.algorithmVersion.*`) to be the existing Algorithm version setting already documented in [Settings](settings.md) (`v1`="Linear", `v2`="Sinusoidal", `v3`="Sinusoidal and hyperbolic" — the mockup shows the default `v3`), just copy-labeled "Chroma velocity" in the UI; confirmed by the requester as governing the global scale algorithm, unrelated to gamut and unrelated to [Hue/Chroma Distribution](hue-chroma-distribution.md)'s shift-curve concept despite the naming similarity

## Problem

Today, exported color values are only ever computed for the sRGB gamut — there's no way to tell the app a palette is meant to be viewed on wide-gamut displays (P3 on modern Apple hardware, Rec. 2020 on some professional/broadcast displays) and get color values that actually use that extra range instead of being silently clamped to sRGB. The ticket frames this as a per-palette optimization, not a replacement: sRGB stays the default and the maximally-compatible choice; Display P3 and Rec. 2020 are opt-in extensions for palettes explicitly authored for wide-gamut screens.

## User flow

1. In the palette's Settings panel, "Color management" section (see [Settings](settings.md) — the same section that already holds Color space / Vision simulation / Algorithm version), the user picks a **Gamut** from a new dropdown — shown first in that section per the Figma mockup, above the existing Color space dropdown: `sRGB` (default), `Display P3`, `Rec. 2020`.
2. **Default is `sRGB`** for every new palette — no visible change for a user who never touches this control, mirroring the "no regression for untouched settings" pattern already used elsewhere in this vault (e.g. [Hue/Chroma Distribution](hue-chroma-distribution.md)'s `LINEAR` default).
3. The choice is scoped to **that palette only** — not a global/app-level preference — same scoping as `colorSpace`/`algorithmVersion` today (see [Palette](../01-domain-model/palette.md) §1, `Base`).
4. When the palette is exported, emitted color values reflect the selected gamut:
   - `sRGB`: byte-for-byte identical to today's output — no behavior change.
   - `Display P3`: values expressed as `color(display-p3 r g b)`.
   - `Rec. 2020`: values expressed as `color(rec2020 r g b)`.
   (Confirmed by the ticket only for CSS-flavored output — see Open questions for which export formats beyond CSS/SCSS/LESS this actually reaches.)
5. On a standard sRGB screen, a palette authored in Display P3 or Rec. 2020 is expected to display "sans perte visible" (no visible loss) — per the ticket's acceptance criteria, colors fold back/clamp correctly, with `sRGB` as the absolute fallback.
6. **Proactive detection, not just silent fallback — confirmed by the requester**: rather than uniformly relying on a fallback for every color regardless of need, the app detects in advance which specific colors would actually be visibly degraded on a gamut-incompatible screen (i.e., colors meaningfully outside sRGB after being authored in `Display P3`/`Rec. 2020`) and surfaces that with a **warning IconChip** — the same warning-affordance pattern already used elsewhere in this vault for a comparable "flag it, don't silently swallow it" case (see [Structure](structure.md)'s broken-binding-link IconChip). Exact placement (per-shade in the color list, or a summary warning in Settings next to Gamut) isn't pinned down by a mockup yet — see Implementation notes.

## Rules

- **Three gamuts, exactly as the ticket names them**: `sRGB` (default), `Display P3`, `Rec. 2020` — no other gamut is in scope.
- **Per-palette, not global**: the gamut is part of a palette's own settings (`Base`, alongside `colorSpace`/`algorithmVersion`), not a workspace- or account-level preference.
- **Backward compatible by construction**: a palette that never touches this setting (or explicitly stays on `sRGB`) produces identical export output to today — matching the "sRGB default" acceptance criterion verbatim.
- **Additive persistence, no migration needed**: unlike [Hue/Chroma Distribution](hue-chroma-distribution.md)'s breaking shift-value shape change, adding `gamut` as a new optional field defaulting to `sRGB` doesn't require rewriting any existing stored palette — an old record simply has no `gamut` key and reads as `sRGB`.
- The engine (`engine-ui-color-palette`) owns the actual color-space conversion/serialization for `Display P3`/`Rec. 2020` — out of scope for this UI-facing spec to redefine.
- **Not Pro-gated** — confirmed by the requester. Unlike Color space's/Vision simulation's per-option plan gating documented in [Settings](settings.md), Gamut is available regardless of plan.
- **Scope is the produced hex values (and the palette's underlying color data), not each export format's own notation** — confirmed by the requester. This is a genuinely different mechanism from Export's existing CSS `color()` "P3" notation choice (see below): here, the actual computed hex for every shade changes with the selected gamut, and that recomputed hex is what every consumer (preview, export, sync) then inherits.
- **Export's existing "P3" color-space option is out of scope and untouched — confirmed resolved**: [Export](export.md)'s CSS/SCSS/LESS color-space sub-picker (`RGB, HEX, HSL, LCH, OKLCH, P3`, keys `export.colorSpace.*`/`settings.color.colorSpace.*`) is purely a **CSS4 notation choice** applied on top of already sRGB-computed values — no real gamut conversion happens in the engine for it today, and it is **not** to be modified by this ticket. It is a separate, orthogonal mechanism from this spec's `gamut` setting, which does drive real engine-side computation.
- **sRGB is the absolute fallback**: when the palette's selected gamut (`Display P3`/`Rec. 2020`) isn't supported by the viewing screen, colors must fall back to sRGB — confirmed as a requirement to build (not assumed to be automatically handled for free by every consumer/platform).
- **Switching gamut recomputes the palette's actual color data** — confirmed by the requester: hex values and the palette's underlying data are updated when the gamut changes, the same class of full-recompute operation as switching `colorSpace`/`algorithmVersion` today, not a lightweight export-time-only transform.
- **Detection-plus-warning, confirmed mechanism for the fallback**: the fallback isn't just a silent, uniform substitution applied to every color — the app is expected to detect, per color, whether that color actually falls outside the sRGB gamut it's about to be viewed on, and surface a **warning IconChip** for the ones that would be visibly degraded, rather than leaving the user to discover clipping on their own. Confirmed by the requester; exact UI placement is an implementation detail (see Implementation notes).

## Acceptance criteria

- [ ] Given an exported palette, when the `sRGB` gamut is selected (the default), then color values are identical to today's behavior — full backward compatibility.
- [ ] Given a palette exported with the `Display P3` gamut, when export is triggered, then color values are expressed in the Display P3 color space (`color(display-p3 …)`).
- [ ] Given a palette exported with the `Rec. 2020` gamut, when export is triggered, then color values are expressed in the Rec. 2020 color space.
- [ ] Given the palette Settings panel, then Gamut is configurable per palette (not globally): the choice is specific to that palette and persisted with it.
- [ ] Given a newly created palette, then its gamut defaults to `sRGB`.
- [ ] Given the Settings panel's Color management section, then a Gamut selector is exposed with exactly three options: `sRGB` (default), `Display P3`, `Rec. 2020`.
- [ ] Given a palette authored in `Display P3` or `Rec. 2020` and viewed on a standard sRGB screen, then colors are correctly folded back (fallback) without visible loss — `sRGB` is the absolute fallback.
- [ ] Given the Gamut setting, when a user on any plan (not just Pro) opens it, then it's available and not blocked by a trial/upgrade prompt.
- [ ] Given a palette's gamut is changed, then its hex values and underlying color data are recomputed to reflect the new gamut — not only the export-time output.
- [ ] Given a color that would be visibly degraded on a screen incompatible with the palette's selected gamut, then it's flagged with a warning IconChip (detected proactively, not left for the user to notice on their own) — colors that wouldn't actually be affected are not flagged.

## Out of scope

- The exact color-space conversion/gamut-mapping math (how a color's coordinates are recomputed for `display-p3`/`rec2020`, and how the sRGB fallback is derived) — engine work (`engine-ui-color-palette`), referenced here but not redefined at the algorithm level.
- **Non-CSS export formats' *native* wide-gamut representations** (e.g. Swift/UIKit's `UIColor(displayP3Red:...)`, Android's `ColorSpace.Named.DISPLAY_P3`) — **Claudian's recommendation, pending sign-off**: keep v1 scoped strictly to the recomputed hex value (consumed as-is by every export format today, CSS or not) and the CSS `color()` notation for web-flavored formats — do **not** build bespoke native wide-gamut constructors for Swift/Android as part of this ticket. Rationale: the ticket's own resources (MDN `color()`, the Figma API note) are entirely CSS/web-oriented, native wide-gamut color needs a fundamentally different data shape than a hex string (a tagged color-space object, not interchangeable with the rest of the export pipeline), and nothing in the ticket or mockup asks for it. If a genuine need for native wide-gamut export surfaces later, treat it as its own follow-up ticket rather than folding it into this one.
- **Resolved, confirmed out of scope**: modifying Export's pre-existing "P3" CSS notation option (`export.colorSpace.p3` / `settings.color.colorSpace.p3`) — confirmed to be a separate, purely-notational mechanism with no real engine-side conversion; not touched by this ticket (see Rules).
- Any change to vision-simulation or contrast-score (WCAG/APCA) computation for non-sRGB values — not mentioned by the ticket.
- **Resolved, confirmed unrelated**: the "Chroma velocity" field visible in the same Figma "Gamut" frame's Color management section — confirmed to be the pre-existing Algorithm version setting (already documented in [Settings](settings.md)), not a new field and not connected to gamut or to [Hue/Chroma Distribution](hue-chroma-distribution.md)'s curve concept (see Design above).

## Implementation notes

No implementation exists yet. What has to be built, concretely:

- **Engine (`engine-ui-color-palette`) — needs a new color-science library, not `chroma-js`**: color serialization/computation needs to become genuinely gamut-aware — today it's implicitly sRGB-only. `chroma-js` (if that's what's used today for color math) isn't expected to handle real `display-p3`/`rec2020` gamut conversion and mapping correctly — a different library needs to be evaluated and picked (e.g. `colorjs.io` / Color.js, which has first-class CSS Color 4 gamut support including `srgb`/`display-p3`/`rec2020` and built-in gamut-mapping, or `culori`, which also models these spaces) — exact library choice is an implementation decision, not settled here (see Open questions). This engine work covers: computing each shade's hex in the selected gamut, and computing the `sRGB` fallback value for screens that don't support the wider gamut.
- **UI — Settings module** (`src/ui/modules/settings`): a new Gamut dropdown in the existing "Color management" section (see [Settings](settings.md)), positioned before Color space per the Figma mockup's field order. Likely follows the exact same wiring as the neighboring Color space dropdown (single generic settings-update callback, applies immediately, no confirmation dialog, not plan-gated — see Settings' Implementation notes and Rules above).
- **UI — per-color warning IconChip**: on gamut change (or on palette load with a non-`sRGB` gamut already set), each color/shade needs an in-gamut check against the target screen's capability, surfacing a warning IconChip on the ones that would actually be visibly degraded — mirrors [Structure](structure.md)'s existing broken-binding-link IconChip pattern (warning chip + helper text on the affected row) closely enough to reuse that same UI primitive. Exact placement (the source-color list in Edit mode? a summary in Settings next to the Gamut dropdown? both?) isn't fixed by a mockup yet — left as a build-time decision, not blocking this spec.
- **Bridges**: `SettingsMessage` (`'UPDATE_SETTINGS'`, handled by `updates/updateSettings.ts`) currently carries `{ name, description, colorSpace, visionSimulationMode, algorithmVersion, textColorsTheme }` (see [`04-contracts/events-messages.md`](../04-contracts/events-messages.md)) — needs a `gamut` field added, mirroring how `colorSpace` is already carried. Since changing gamut recomputes the palette's actual color data (confirmed, see Rules), this likely needs to trigger the same kind of full palette recompute+re-notify already done for `colorSpace`/`algorithmVersion` changes, not just a stored-preference update.
- **API / MCP — confirmed shape**: `POST /v1/generate-code` already accepts `colorSpace` (see [`04-contracts/api-endpoints.md`](../04-contracts/api-endpoints.md)); `gamut` is added as its own **sibling** request param, not folded into the existing `colorSpace` enum — confirmed by the requester, and consistent with `gamut` being added as its own field everywhere else in this spec (`Base.gamut`, the `gamut` DB column, `SettingsMessage.gamut`). `mcp-ui-color-palette`'s `generate_code` tool mirrors this endpoint 1:1 and would need the same change.
- **Local & cloud persistence — confirmed shape**:
  - `Base` (see [Palette](../01-domain-model/palette.md) §1) gains a new field: **`gamut: 'SRGB' | 'P3' | 'REC2020'`**, alongside `colorSpace`/`algorithmVersion` — additive and defaulting to `'SRGB'`, so no blocking migration is needed (contrast with [Hue/Chroma Distribution](hue-chroma-distribution.md), which does require one). This same field needs adding to `FullConfiguration`/`ExchangeConfiguration`/`PaletteData` (`engine-ui-color-palette/src/types/configuration.types.ts` / `data.types.ts`) and to the local-document storage shape (Figma `setSharedPluginData` / web `localStorage`, per host, same as every other `Base` field).
  - **Cloud (Supabase)**: a new **`gamut` `text` column** on the palettes table, alongside the existing fixed column list already referenced in [Structure](structure.md)'s Implementation notes (`palette_id, name, description, preset, shift, colors, themes, color_space, algorithm_version, ...`). `api-ui-color-palette/src/handlers/community.ts`'s publish/list/star handlers need `gamut` added to their select/insert column list, and `PUBLISH_PALETTE`/`SYNC_PALETTE`/`PULL_PALETTE` need to read/write it like `color_space`/`algorithm_version` already do.
- **Platforms**: the ticket's own resources flag "Figma API — color variables et gamuts" as worth checking — whether Figma's Variables API (or Penpot/Sketch/Framer equivalents) natively support a non-sRGB color space for synced variables/styles isn't established; today's shared bridge catalog ([`03-platform-bridges/bridge-actions.md`](../03-platform-bridges/bridge-actions.md)) has no gamut-related branching anywhere. Left open.
- **Analytics**: no existing event covers this. A new `SettingEvent` feature value (alongside the existing `UPDATE_COLOR_SPACE`) is the natural fit, following the same per-module event pattern documented in [`04-contracts/events-messages.md`](../04-contracts/events-messages.md).
- **Localization (Tolgee)**: confirmed via the Tolgee MCP — project `UI Color Palette・Plugins` (id `2`), flat dot-prefixed keys, no namespaces (same convention already used by every sibling field in this section). Full copy inventory below.

## Open questions

- **Engine library choice — deliberately left open**: confirmed direction is *not* `chroma-js` for the real gamut conversion/mapping math, but the requester explicitly chose not to pin the replacement now. `colorjs.io` and `culori` remain the plausible candidates noted in Implementation notes, to be settled via an actual spike at implementation time, not decided in this spec.
- **Native (Swift/Android) wide-gamut export — recommendation given, not yet confirmed**: see Out of scope for Claudian's suggested resolution (keep v1 to hex + CSS `color()` only); this still needs explicit sign-off from the requester before being treated as settled.
- **Exact placement of the per-color warning IconChip**: the detection-plus-warning mechanism itself is confirmed (see Rules/User flow), but which screen(s) show it — the color list in Edit mode, a Settings-level summary, both — isn't fixed by a mockup yet.

~~**sRGB fallback mechanism**~~ — resolved: not a silently-substituted second hex, but a proactive per-color check that surfaces a warning IconChip for colors that would actually be visibly degraded (see Rules/User flow/Acceptance criteria).

~~**`gamut` request param shape for `/generate-code`/MCP**~~ — resolved: confirmed as its own sibling param, not folded into `colorSpace` (see Implementation notes).
