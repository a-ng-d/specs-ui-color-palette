# Feature — Hue/Chroma Distribution (non-linear shift curves)

- **Status**: Draft
- **Package(s) concerned**: `ui-ui-color-palette` (UI controls — not implemented yet), `engine-ui-color-palette` (curve/interpolation math — not implemented yet, new `ShiftConfiguration` shape), local & cloud persistence (migration of existing shift data — not implemented yet)
- **UI module**: no new module/mode — modifies two existing ones: `src/ui/modules/scale` (global hue/chroma sliders **and** the panel's overall sectioning/velocity system, see [Scale](scale.md)) and `src/ui/contexts/Colors.tsx` (per-color hue/chroma shift, see [Colors](colors.md)). `src/ui/modules/settings` is referenced for contrast only (its unrelated `algorithmVersion`/"Chroma velocity" gamut-mapping control, confirmed untouched by this spec — see Rules)
- **Related spec**: [Scale](scale.md) (§ global hue/chroma shift, § distribution easing), [Colors](colors.md) (§ per-color hue/chroma shift), [Settings](settings.md) (§ `algorithmVersion` — a distinct, unrelated gamut-mapping mechanism, confirmed not touched by this spec), [Palette](../01-domain-model/palette.md) §2/§4 (`ShiftConfiguration`, `SHIFT_HUE`/`SHIFT_CHROMA`/`RESET_HUE`/`RESET_CHROMA` actions)
- **Ticket**: Notion — "Distribution non-linéaire du décalage de hue et du chroma sur les extrémités de la palette" (`POR-642`), sourced from a Canny request ("[Separate saturation adjustments for shades and tints](https://ui-color-palette.canny.io/feature-requests/p/seperate-saturation-adjustments-for-shades-and-tints)"). P2, 8 story points, targets power users wanting fine control over the palette's curve.
- **Design**: Figma — `UICP Screens` file, section **"Chroma-Hue Flow"** (node `4972:31594`), two frames: `Scale` (`4968:9104` — global panel) and `Colors` (`4955:11263` — per-color "parameters" panel)

## Problem

Today, hue and chroma shift are each a single flat value applied as a **uniform additive offset across every stop of the scale** (see [Scale](scale.md) — "global offsets applied to the whole scale, not per-stop" — and [Colors](colors.md) for the per-color equivalent). A power user can't currently make the shift bite harder at the extremities of the scale (the darkest shades and the lightest tints) while leaving the stops near the source color closer to untouched — the Canny request this ticket originates from asks specifically for **separate saturation adjustments for shades vs. tints**. This spec scopes introducing a **curve** to the existing shift controls: an **interpolation between each extremity and the middle of the scale**, aiming for a scale that reads as more natural, while giving the user explicit numeric control over the values — `LINEAR` (flat, today's behavior), `HYPERBOLA` (the same value at both extremities, interpolating through neutral at the middle), and `FREE` (a different value at each extremity, same middle interpolation).

This sits alongside two other, pre-existing "make the scale look more natural" mechanisms already in the product — confirmed by the requester to be genuinely distinct from this one and from each other, worth naming precisely so implementation doesn't conflate them:

- **`algorithmVersion`** ([Settings](settings.md), real UI label "Chroma velocity" — `Linear`/`Sinusoidal`/`Sinusoidal and hyperbolic`): the *sense* of the scale, driven by different mathematical functions, to get a more natural-looking light↔dark scale. Global to the whole palette. Its three modes are **successive product-algorithm generations over time**, not three interchangeable styles.
- **"Distribution easing"** ([Scale](scale.md), curve × velocity): how the **stops themselves are positioned relative to each other**, based on an acceleration — hence the animation-easing vocabulary (`Sine`/`Quad`/`Cubic`/`Ease in`/`Ease out`).
- **This ticket's shift curve**: interpolates the **hue/chroma shift amount** between the scale's extremities and its middle — same underlying "more natural scale" goal as the two mechanisms above, but a different axis (shift magnitude, not lightness computation or stop position), with direct numeric control exposed to the user.

The Scale panel's overall structure is also confirmed to need an evolution alongside this — **clearer sectioning**, and presenting the shift-curve selector as **tabs** rather than icon buttons. Exactly how far that "tabs" reorganization extends (e.g. whether Distribution easing's own selector also becomes tab-based, or only the new shift curve does) isn't nailed down yet — see Open questions.

## User flow

1. Both the global shift controls (Scale mode's Hue/Chroma sliders) and the per-color shift controls (Colors' "more parameters" panel, per row) gain a **curve-mode selector** — `LINEAR`/`HYPERBOLA`/`FREE`, presented as **tabs** (the current Figma mockup still shows this as three icon buttons — a flat line, a symmetric dip, an S-curve — pending a design update to match the confirmed tabs direction, see Rules).
2. **Default is `LINEAR`** — the control looks and behaves exactly as it does today (a single value field, e.g. "Value" globally or "Shift chroma: `C 100%`" per-color): no visible change for a user who never touches the new curve selector.
3. Switching to `HYPERBOLA` keeps a **single** value field, now applied identically to both extremities of the scale rather than flat everywhere. Switching to `FREE` replaces it with **two independently editable threshold fields**, shown in the UI as `L`/`R` (left/right) at both levels — confirmed as the clearer UI framing, even though the global Scale panel's current Figma mockup still shows `Min`/`Max` copy for its two-field state (see Rules: `min`/`max` stays as the technical/data-model field name, not as UI copy).
4. The palette preview updates in real time as either threshold is dragged/typed, same as today's live-update behavior for the flat shift value.
5. The curve is picked **independently for hue and for chroma** — a palette can have, say, `LINEAR` hue and `FREE` chroma at the same time.
6. The same curve system exists at **both levels**: the global palette-wide shift (Scale) and the per-color shift (Colors) — mirroring how [Colors](colors.md) already layers a per-color shift on top of the palette-wide one today, just with `curve`/`min`/`max` added to both layers.
7. On an individual color, **Reset** restores that color's hue/chroma shift (value **and** curve/min/max) back to the palette-wide shift — same mechanic as today's "locked" per-color shift reset (see [Colors](colors.md) Rules), extended to the new fields.
8. The **Scale panel is reorganized with better sectioning** (clearer, more distinct blocks — Lightness / Chroma / Hue — matching the Figma mockup's already-separated sections), and the **shift-curve selector (`LINEAR`/`HYPERBOLA`/`FREE`) is presented as tabs** rather than icon buttons — a UI-presentation change to this ticket's own control, distinct from (and not merged with) the panel's other existing curve-like controls (Distribution easing, `algorithmVersion`), which keep their current presentation and behavior untouched.

## Rules

- **Three curves, confirmed UI order `LINEAR` → `HYPERBOLA` → `FREE`** — **`HYPERBOLA`'s definition corrected here after an earlier misreading in this spec, see History**:
  - `LINEAR` (default): the shift `value` is applied directly and uniformly across every stop — today's exact behavior, unchanged. Backward compatible by construction.
  - `HYPERBOLA`: **the same value is used at both extremities** (`min` = `max`, literally) — the user edits a single number, applied identically left and right; the curve interpolates that shared value down (or up) through neutral (0) at the scale's middle, then back to the same value at the opposite extremity. This matches the ticket's original "a single fixed value" wording exactly — confirmed correct by the requester; an earlier draft of this spec had incorrectly "corrected" this into a mirrored/negated-pair reading, which was wrong.
  - `FREE`: **a different value at each extremity** (`min` ≠ `max` allowed) — `L`/`R` are edited independently, same middle-neutral interpolation, just asymmetric endpoints (e.g. `L 12° → 0 → R -5°`).
  - Beyond which values are equal/independent, the exact mathematical interpolation function used to compute intermediate stops between an extremity and the middle is engine work, out of scope for this UI-facing spec.
- **New data model** (per the ticket, replacing today's single numeric shift value):
  - Global (palette-wide) shift:
    ```typescript
    shift: {
      hue: { min: 5, max: 12, value: 4, curve: 'LINEAR' | 'HYPERBOLA' | 'FREE' },
      chroma: { min: 46, max: 123, value: 130, curve: 'LINEAR' | 'HYPERBOLA' | 'FREE' },
    }
    ```
  - Per-color shift (nested under each color, alongside the existing `isLocked`):
    ```typescript
    hue: { shift: { min, max, value, curve }, isLocked: boolean }
    chroma: { shift: { min, max, value, curve }, isLocked: boolean }
    ```
  - All three of `value`/`min`/`max` coexist in the type regardless of the active `curve` — switching curves is expected to be non-destructive (e.g. flipping from `FREE` back to `LINEAR` doesn't discard whatever `min`/`max` were last set, and vice versa), even though only the fields relevant to the active curve are shown in the UI at a given time.
- **`min`/`max` vs. `L`/`R` — resolved**: `min`/`max` are kept as the technical/data-model field names (confirmed to keep as-is), but the **UI copy shows `L`/`R` (left/right threshold) at both levels** — the per-color panel's mockup already does this; the global Scale panel's current mockup copy (`Min`/`Max`) should be updated to match for consistency, not kept as a second, different label for the same concept.
- **Field-count-follows-curve — refined**: `LINEAR` shows a single value field (unchanged from today). `HYPERBOLA` also shows a **single** value field, since the same value applies to both extremities by definition — no second field needed. `FREE` shows **two** independently-editable `L`/`R` fields (confirmed by the per-color mockup, e.g. `L 12°`/`R -5°`) — the only one of the three curves with two user-editable fields.
- **Per-color shift keeps its existing "locked" semantics** ([Colors](colors.md)): a per-color hue/chroma shift is flagged locked once it diverges from the palette-wide shift; Reset clears the whole shift object (value, curve, min, max) back to the palette-wide one — this rule now covers the new fields too, not just the old single value.
- The engine (`engine-ui-color-palette`) owns the actual interpolation math distinguishing `HYPERBOLA`'s fixed curve shape from `FREE`'s free-form one — out of scope for this UI-facing spec to redefine, but the shift-computation logic that today applies a flat offset per stop needs to become curve-aware and threshold-aware.
- **Scale panel evolution — three distinct "more natural scale" mechanisms, not to be conflated (see Problem)**: `algorithmVersion` ([Settings](settings.md), "Chroma velocity") drives the palette-global lightness *sense* via successive versioned math functions; "Distribution easing" ([Scale](scale.md)) positions lightness stops relative to each other via acceleration; this ticket's shift curve interpolates the hue/chroma shift amount between extremities and middle. All three stay separate — `algorithmVersion` and Distribution easing are confirmed **untouched** by this spec, not merged, renamed, or superseded.
- **Better sectioning**: the Scale panel's Lightness/Chroma/Hue blocks (already visually separated in the current Figma mockup) are confirmed to gain clearer structural separation, and the shift-curve selector moves from icon buttons to **tabs** — a presentation change scoped to this ticket's own control.
- **Exact scope of the "tabs" reorganization isn't fully nailed down**: whether Distribution easing's own selector also becomes tab-based as part of this same visual pass, or only the new shift curve does, isn't confirmed (see Open questions).
- **Migration — mechanism confirmed, two tracks**: every existing palette (local documents and cloud/published records) stores hue/chroma shift as a bare number today. **Local data** is migrated **at plugin runtime**, via a dedicated conversion method built to fail safe (no thrown exceptions) rather than a one-time versioned migration step — it runs whenever the plugin loads a palette, tolerating already-migrated or malformed data. **Cloud/database data** is migrated separately, via a **SQL function** run against the Supabase-backed palettes table, not through application code. Either way, the result is `{ min, max, value, curve: 'LINEAR' }` (old number → `value`, `curve` defaulted to `LINEAR`) — "sans erreur ni régression sur les palettes déjà enregistrées" per the ticket.

## Acceptance criteria

- [ ] Given a palette with a configured hue shift, when the user enables extremity distribution (a non-`LINEAR` curve), then the hue shift is applied concentrated on the shades/tints ends of the scale rather than uniformly across every step.
- [ ] Given a palette with an adjusted chroma shift, when non-linear distribution is enabled, then chroma varies independently for shades vs. tints.
- [ ] Given `LINEAR` mode (the default), then behavior is byte-for-byte identical to today's flat-offset shift — no regression for palettes that never touch the new curve controls.
- [ ] Given the shift controls (global or per-color), when the user switches curve, then the control's field layout follows: one value field for `LINEAR`, one value field for `HYPERBOLA` (applied to both extremities equally), two independently-editable `L`/`R` threshold fields for `FREE` — with the same `L`/`R` labeling at both levels (global Scale panel copy updated to match the per-color panel's).
- [ ] Given a curve set to `HYPERBOLA` or `FREE`, when the resulting shift is computed across the scale, then it interpolates from the left extremity value, through neutral (0) at the scale's midpoint, to the right extremity value — for `FREE` this may be asymmetric (e.g. `L 12°` / `R -5°`), while `HYPERBOLA`'s left/right values are always equal by construction.
- [ ] Given curve `HYPERBOLA`, then a single value is user-editable and applies identically to both extremities — not independently settable per side.
- [ ] Given curve `FREE`, then both threshold fields (`L`/`R`) are independently editable, with no equality constraint between them.
- [ ] Given the palette preview, when a threshold or value is edited, then the preview updates in real time, matching today's live-update behavior.
- [ ] Given a palette with a non-`LINEAR` curve configured, when the palette is saved, then the full shift shape (`min`/`max`/`value`/`curve`) is persisted with the palette, both locally and once published/synced to the cloud.
- [ ] Given hue and chroma on the same palette/color, when their curves are set independently, then each behaves according to its own curve setting without affecting the other.
- [ ] Given the global (palette-wide) level and the per-color level, then both expose the same three curves (`LINEAR`/`HYPERBOLA`/`FREE`, in that order), configurable independently at each level.
- [ ] Given a per-color shift, when the user hits Reset, then the color's hue/chroma shift (value, curve, min, and max) is restored to the palette-wide shift — not just the value, as today's Reset already does for the old single-value shift.
- [ ] Given an existing local palette opened after this ships, when the plugin loads it, then a runtime conversion (not a versioned migration step) reads its hue/chroma shift correctly as `{ min, max, value, curve: 'LINEAR' }`, without throwing on already-migrated or malformed data.
- [ ] Given an existing cloud/published palette, when the database-side SQL migration function runs, then its hue/chroma shift is converted to `{ min, max, value, curve: 'LINEAR' }` with no data loss and no read errors afterward.
- [ ] Given the Scale panel, then Lightness, Chroma, and Hue are presented as clearly separated sections, each with room for its own curve selector.
- [ ] Given the shift-curve selector (`LINEAR`/`HYPERBOLA`/`FREE`), then it's presented as tabs rather than icon buttons, at both the global Scale panel and the per-color Colors panel.
- [ ] Given `Settings`' existing `algorithmVersion` control and Scale's existing "Distribution easing", when this feature ships, then both continue to behave and present exactly as they do today — untouched, not merged into or superseded by this ticket's shift curve.

## Out of scope

- The actual interpolation formula/math used between an extremity value and neutral at the middle (how `min`/`max`/`value` combine to produce a per-stop shift) — that's engine work (`engine-ui-color-palette`), referenced here but not redefined; this spec covers the UI-facing contract (fields shown, persistence shape, migration) only.
- Any redesign of the existing flat-shift UX for `LINEAR` mode — explicitly required to stay identical to today.
- Redesigning [Settings](settings.md)'s existing `algorithmVersion`/"Chroma velocity" (global lightness-sense via versioned math functions) — confirmed to be a distinct, unrelated mechanism that stays exactly as-is; not merged, renamed, or removed by this spec.
- Redesigning [Scale](scale.md)'s existing "Distribution easing" (lightness stop-position/acceleration curve) beyond whatever shared visual treatment the "better sectioning" pass happens to apply — its own values/behavior aren't changed by this spec.
- The exact implementation of the local runtime-safe conversion (e.g. whether it caches its result or re-runs every load) and of the cloud SQL migration function (naming, whether it's a one-off script or a repeatable function) — mechanism is confirmed (see Rules), exact code is an implementation detail for whoever builds this.

## Implementation notes

No implementation exists yet. What has to be built, concretely:

- **Engine (`engine-ui-color-palette`)**: `ShiftConfiguration`'s hue/chroma shape needs to grow from a bare number to `{ min, max, value, curve }`; the stop-by-stop shift-application logic needs to become curve-aware (flat passthrough for `LINEAR`, threshold interpolation through neutral at the midpoint for `HYPERBOLA`/`FREE`, differing only in the shape of that interpolation function and in whether `min`/`max` are forced equal (`HYPERBOLA`) or independent (`FREE`)).
- **UI — Scale module** (`src/ui/modules/scale`): the existing global hue/chroma sliders (see [Scale](scale.md) Rules — "global offsets applied to the whole scale") need the 3-way curve selector (`LINEAR`/`HYPERBOLA`/`FREE`, in that order), presented as **tabs**, with the field layout varying by curve (one field for `LINEAR`, one field for `HYPERBOLA` applied to both extremities, two independent `L`/`R` fields for `FREE` — see Rules) — note the current Figma mockup labels these `Min`/`Max` at the global level, which per the confirmed decision should become `L`/`R` copy to match the per-color panel (the underlying field names stay `min`/`max`). Additionally, the panel needs restructuring into clearer Lightness/Chroma/Hue sections — a presentation change, not touching `algorithmVersion` or Distribution easing's own math (see Rules).
- **UI — Colors module** (`src/ui/contexts/Colors.tsx`): the existing per-color "more parameters" panel (see [Colors](colors.md) User flow step 3) needs the same curve selector plus the value-field ↔ `L`/`R`-field toggle shown in the Figma `Colors` frame's "parameters" panel — and Reset needs to clear the full new shape, not just a single value.
- **Bridges**: both `UPDATE_SCALE` (global shift, per [Scale](scale.md)) and `UPDATE_COLORS` (per-color shift, per [Colors](colors.md)) already carry hue/chroma shift as part of their existing full-payload messages — their payload shape needs to grow to the new `{min,max,value,curve}` object; no new message type is obviously needed, but worth confirming against the actual bridge code once this is picked up.
- **Local persistence — migration**: every stored local palette holds hue/chroma shift as a bare number today; confirmed direction is a **runtime conversion method** (not a versioned migration step) that runs whenever the plugin loads a palette, built to fail safe (no thrown exceptions) on already-migrated or malformed data, converting to `{ min, max, value, curve: 'LINEAR' }`.
- **Cloud persistence — migration**: confirmed direction is a **SQL function** run directly against the Supabase-backed palettes table, separate from and not dependent on the local runtime conversion — zero tolerance for data loss or read errors on existing published palettes.
- **Analytics**: [Scale](scale.md) already flags that hue/chroma shift changes aren't tracked at all today (confirmed gap in that spec); [Colors](colors.md) does track `SHIFT_HUE`/`SHIFT_CHROMA`/`RESET_HUE`/`RESET_CHROMA` per-color. Adding curve-mode tracking (which of `LINEAR`/`HYPERBOLA`/`FREE` was picked) should piggyback on however those gaps get closed, rather than introducing a separate, inconsistent tracking scheme.
- **Platforms**: shared core logic per the ticket ("Tous les éditeurs concernés") — no platform-specific branching expected, consistent with how [Scale](scale.md)/[Colors](colors.md) already work identically across Figma/Penpot/Sketch/Framer.
