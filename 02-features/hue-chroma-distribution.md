# Feature — Hue/Chroma Distribution (non-linear shift curves)

- **Status**: Draft
- **Package(s) concerned**: `ui-ui-color-palette` (UI controls — not implemented yet), `engine-ui-color-palette` (curve/interpolation math — not implemented yet, new `ShiftConfiguration` shape), local & cloud persistence (migration of existing shift data — not implemented yet)
- **UI module**: no new module/mode — modifies two existing ones: `src/ui/modules/scale` (global hue/chroma sliders **and** the panel's overall sectioning/velocity system, see [Scale](scale.md)) and `src/ui/contexts/Colors.tsx` (per-color hue/chroma shift, see [Colors](colors.md)). `src/ui/modules/settings` is referenced for contrast only (its unrelated `algorithmVersion`/"Chroma velocity" gamut-mapping control, confirmed untouched by this spec — see Rules)
- **Related spec**: [Scale](scale.md) (§ global hue/chroma shift, § distribution easing), [Colors](colors.md) (§ per-color hue/chroma shift), [Settings](settings.md) (§ `algorithmVersion` — a distinct, unrelated gamut-mapping mechanism, confirmed not touched by this spec), [Palette](../01-domain-model/palette.md) §2/§4 (`ShiftConfiguration`, `SHIFT_HUE`/`SHIFT_CHROMA`/`RESET_HUE`/`RESET_CHROMA` actions)
- **Ticket**: Notion — "Distribution non-linéaire du décalage de hue et du chroma sur les extrémités de la palette" (`POR-642`), sourced from a Canny request ("[Separate saturation adjustments for shades and tints](https://ui-color-palette.canny.io/feature-requests/p/seperate-saturation-adjustments-for-shades-and-tints)"). P2, 8 story points, targets power users wanting fine control over the palette's curve.
- **Design**: Figma — `UICP Screens` file, section **"Chroma-Hue Flow"** (node `4972:31594`), two frames: `Scale` (`4968:9104` — global panel) and `Colors` (`4955:11263` — per-color "parameters" panel)

## Problem

Today, hue and chroma shift are each a single flat value applied as a **uniform additive offset across every stop of the scale** (see [Scale](scale.md) — "global offsets applied to the whole scale, not per-stop" — and [Colors](colors.md) for the per-color equivalent). A power user can't currently make the shift bite harder at the extremities of the scale (the darkest shades and the lightest tints) while leaving the stops near the source color closer to untouched — the Canny request this ticket originates from asks specifically for **separate saturation adjustments for shades vs. tints**. This spec scopes introducing a **curve** to the existing shift controls, so hue/chroma shift can be distributed non-linearly instead of flat.

This also surfaces a second, closely related gap the requester flagged directly: the Scale panel's overall structure needs an evolution alongside this — **clearer sectioning**, and a **new "velocity" control presented as tabs** that acts on lightness and, newly, on the palette's global hue/chroma shift. This is confirmed to be a **distinct, additional axis**, not a rename or relocation of either existing curve-shaped mechanism already in the product — specifically ruled out by the requester (see Rules):
- **Not** [Settings](settings.md)'s existing `algorithmVersion` option (real UI label, confirmed via Tolgee: **"Chroma velocity"**, values `Linear`/`Sinusoidal`/`Sinusoidal and hyperbolic`) — that control acts **jointly on lightness and chroma together, to converge the result onto the sRGB gamut**; it's a gamut-mapping strategy, unrelated to the hue/chroma shift this ticket introduces.
- **Not** [Scale](scale.md)'s existing "Distribution easing" (curve × velocity) either — that system repositions **where lightness stops sit** along the scale; the new velocity concept doesn't do that.

Exactly what the new velocity axis does mechanically (beyond "applies to lightness and to the hue/chroma shift") isn't specified yet — flagged in Open questions rather than guessed.

## User flow

1. Both the global shift controls (Scale mode's Hue/Chroma sliders) and the per-color shift controls (Colors' "more parameters" panel, per row) gain a **curve-mode selector** — three icon buttons, matching the Figma mockup: a flat line (`LINEAR`), a symmetric dip (`HYPERBOLA`), and an S-curve (`FREE`).
2. **Default is `LINEAR`** — the control looks and behaves exactly as it does today (a single value field, e.g. "Value" globally or "Shift chroma: `C 100%`" per-color): no visible change for a user who never touches the new curve selector.
3. Switching to `HYPERBOLA` or `FREE` replaces the single value field with **two independently editable threshold fields**, shown in the UI as `L`/`R` (left/right) at both levels — confirmed as the clearer UI framing, even though the global Scale panel's current Figma mockup still shows `Min`/`Max` copy (see Rules: `min`/`max` stays as the technical/data-model field name, not as UI copy).
4. The palette preview updates in real time as either threshold is dragged/typed, same as today's live-update behavior for the flat shift value.
5. The curve is picked **independently for hue and for chroma** — a palette can have, say, `LINEAR` hue and `FREE` chroma at the same time.
6. The same curve system exists at **both levels**: the global palette-wide shift (Scale) and the per-color shift (Colors) — mirroring how [Colors](colors.md) already layers a per-color shift on top of the palette-wide one today, just with `curve`/`min`/`max` added to both layers.
7. On an individual color, **Reset** restores that color's hue/chroma shift (value **and** curve/min/max) back to the palette-wide shift — same mechanic as today's "locked" per-color shift reset (see [Colors](colors.md) Rules), extended to the new fields.
8. The **Scale panel is reorganized with better sectioning** (clearer, more distinct blocks — Lightness / Chroma / Hue — matching the Figma mockup's already-separated sections) and gains a **velocity control presented as tabs**, shared across sections: it acts on the lightness distribution (as today's existing easing system already does, see [Scale](scale.md)) **and, newly, on the global hue/chroma shift** — surfacing and broadening what exists today only as a hidden, chroma-only Settings option (see Rules).

## Rules

- **Three curves, confirmed UI order `LINEAR` → `HYPERBOLA` → `FREE`**:
  - `LINEAR` (default): the shift `value` is applied directly and uniformly across every stop — today's exact behavior, unchanged. Backward compatible by construction.
  - `HYPERBOLA`: the user edits **a single threshold value**; the engine **mirrors** it to derive the opposite threshold — this is what the ticket's "a single fixed value" wording referred to. The two stored thresholds (`min`/`max`, i.e. `L`/`R`) end up genuinely **different** (e.g. a mirrored/negated pair), not literally equal — confirming the requester's earlier correction that "min = max" (as literal equality) was imprecise, while "driven from a single input" was the real point.
  - `FREE`: the user edits **both thresholds independently** — `L`/`R` (`min`/`max`) can take any two unrelated values, no mirroring.
  - Both `HYPERBOLA` and `FREE` interpolate the shift **from the left threshold, through neutral (0) at the middle of the scale, to the right threshold** — e.g. `L 12° → 0 → R -5°` is a valid, intended configuration, not a contradiction (confirmed directly).
  - Beyond the input mechanism (mirrored single value vs. two independent values), the exact mathematical interpolation function used to compute intermediate stops between the thresholds is engine work, out of scope for this UI-facing spec.
- **New data model** (per the ticket, replacing today's single numeric shift value):
  - Global (palette-wide) shift:
    ```typescript
    shift: {
      hue: { min: 5, max: 12, value: 4, curve: 'LINEAR' | 'HYPERBOLA' | 'FREE' },
      chroma: { min: 46, max: 123, value: 130, curve: 'LINEAR' | 'HYPERBOLA' | 'FREE' },
    }
    ```
  - Per-color shift (nested under each color, alongside the existing `isLocked`):
    ```typescript
    hue: { shift: { min, max, value, curve }, isLocked: boolean }
    chroma: { shift: { min, max, value, curve }, isLocked: boolean }
    ```
  - All three of `value`/`min`/`max` coexist in the type regardless of the active `curve` — switching curves is expected to be non-destructive (e.g. flipping from `FREE` back to `LINEAR` doesn't discard whatever `min`/`max` were last set, and vice versa), even though only the fields relevant to the active curve are shown in the UI at a given time.
- **`min`/`max` vs. `L`/`R` — resolved**: `min`/`max` are kept as the technical/data-model field names (confirmed to keep as-is), but the **UI copy shows `L`/`R` (left/right threshold) at both levels** — the per-color panel's mockup already does this; the global Scale panel's current mockup copy (`Min`/`Max`) should be updated to match for consistency, not kept as a second, different label for the same concept.
- **Field-count-follows-curve — refined**: `LINEAR` shows a single value field (unchanged from today). `FREE` shows two independently-editable `L`/`R` fields (confirmed by the per-color mockup, e.g. `L 12°`/`R -5°`). `HYPERBOLA` shows **one editable field**, its mirrored counterpart derived automatically rather than independently editable — distinct from `FREE`'s two-independent-field layout, per the mirroring rule above.
- **Per-color shift keeps its existing "locked" semantics** ([Colors](colors.md)): a per-color hue/chroma shift is flagged locked once it diverges from the palette-wide shift; Reset clears the whole shift object (value, curve, min, max) back to the palette-wide one — this rule now covers the new fields too, not just the old single value.
- The engine (`engine-ui-color-palette`) owns the actual interpolation math distinguishing `HYPERBOLA`'s fixed curve shape from `FREE`'s free-form one — out of scope for this UI-facing spec to redefine, but the shift-computation logic that today applies a flat offset per stop needs to become curve-aware and threshold-aware.
- **Scale panel evolution — a new, distinct axis, NOT a relocation — corrected by the requester**: an earlier draft of this spec assumed the new "velocity" tabs were the same mechanism as [Settings](settings.md)'s existing `algorithmVersion` option (real UI label, confirmed via Tolgee: **"Chroma velocity"**, values `Linear`/`Sinusoidal`/`Sinusoidal and hyperbolic`), just relocated into Scale. **Confirmed wrong**: `algorithmVersion`/"Chroma velocity" acts **jointly on lightness and chroma together, to converge the computed result onto the sRGB gamut** — a gamut-mapping strategy, unrelated to hue/chroma shift. It stays exactly as-is in Settings, untouched by this spec.
- **Also not the same as lightness's existing "Distribution easing"** (curve × velocity, see [Scale](scale.md)): that system controls **where lightness stops sit** along the scale (stop position), which the new velocity axis does not do either.
- **What the new velocity axis actually does mechanically, beyond applying to lightness and to the hue/chroma shift, isn't specified yet** — genuinely open, not resolved by analogy to either existing mechanism (see Open questions).
- **Better sectioning**: the Scale panel's Lightness/Chroma/Hue blocks (already visually separated in the current Figma mockup) are confirmed to gain clearer structural separation as part of this same evolution — not a cosmetic-only change, but what makes room for the new velocity tabs alongside the per-section curve selectors.
- **Migration — mechanism confirmed, two tracks**: every existing palette (local documents and cloud/published records) stores hue/chroma shift as a bare number today. **Local data** is migrated **at plugin runtime**, via a dedicated conversion method built to fail safe (no thrown exceptions) rather than a one-time versioned migration step — it runs whenever the plugin loads a palette, tolerating already-migrated or malformed data. **Cloud/database data** is migrated separately, via a **SQL function** run against the Supabase-backed palettes table, not through application code. Either way, the result is `{ min, max, value, curve: 'LINEAR' }` (old number → `value`, `curve` defaulted to `LINEAR`) — "sans erreur ni régression sur les palettes déjà enregistrées" per the ticket.

## Acceptance criteria

- [ ] Given a palette with a configured hue shift, when the user enables extremity distribution (a non-`LINEAR` curve), then the hue shift is applied concentrated on the shades/tints ends of the scale rather than uniformly across every step.
- [ ] Given a palette with an adjusted chroma shift, when non-linear distribution is enabled, then chroma varies independently for shades vs. tints.
- [ ] Given `LINEAR` mode (the default), then behavior is byte-for-byte identical to today's flat-offset shift — no regression for palettes that never touch the new curve controls.
- [ ] Given the shift controls (global or per-color), when the user switches curve, then the control's field layout follows: one "Value" field for `LINEAR`, two independently-editable `L`/`R` threshold fields for `HYPERBOLA`/`FREE` — with the same `L`/`R` labeling at both levels (global Scale panel copy updated to match the per-color panel's).
- [ ] Given a curve set to `HYPERBOLA` or `FREE`, when the resulting shift is computed across the scale, then it interpolates from the left threshold, through neutral (0) at the scale's midpoint, to the right threshold — an asymmetric configuration (e.g. `L 12°` / `R -5°`) is expected and valid, not an error.
- [ ] Given curve `HYPERBOLA`, then only one threshold field is user-editable, and the opposite threshold is automatically mirrored/derived from it — not independently settable.
- [ ] Given curve `FREE`, then both threshold fields (`L`/`R`) are independently editable, with no mirroring constraint between them.
- [ ] Given the palette preview, when a threshold or value is edited, then the preview updates in real time, matching today's live-update behavior.
- [ ] Given a palette with a non-`LINEAR` curve configured, when the palette is saved, then the full shift shape (`min`/`max`/`value`/`curve`) is persisted with the palette, both locally and once published/synced to the cloud.
- [ ] Given hue and chroma on the same palette/color, when their curves are set independently, then each behaves according to its own curve setting without affecting the other.
- [ ] Given the global (palette-wide) level and the per-color level, then both expose the same three curves (`LINEAR`/`HYPERBOLA`/`FREE`, in that order), configurable independently at each level.
- [ ] Given a per-color shift, when the user hits Reset, then the color's hue/chroma shift (value, curve, min, and max) is restored to the palette-wide shift — not just the value, as today's Reset already does for the old single-value shift.
- [ ] Given an existing local palette opened after this ships, when the plugin loads it, then a runtime conversion (not a versioned migration step) reads its hue/chroma shift correctly as `{ min, max, value, curve: 'LINEAR' }`, without throwing on already-migrated or malformed data.
- [ ] Given an existing cloud/published palette, when the database-side SQL migration function runs, then its hue/chroma shift is converted to `{ min, max, value, curve: 'LINEAR' }` with no data loss and no read errors afterward.
- [ ] Given the Scale panel, then Lightness, Chroma, and Hue are presented as clearly separated sections, each with room for its own curve selector alongside the new shared velocity tabs.
- [ ] Given the velocity tabs, when the user picks a velocity, then it applies consistently to lightness and to the global hue/chroma shift curve — as its own, independent mechanism, without touching or reading from [Settings](settings.md)'s unrelated `algorithmVersion`/"Chroma velocity" gamut-mapping option.
- [ ] Given `Settings`' existing `algorithmVersion` control, when this feature ships, then it continues to behave exactly as it does today (gamut-mapping across lightness+chroma) — untouched, not merged into or superseded by the new velocity tabs.

## Out of scope

- The actual interpolation formula/math distinguishing `HYPERBOLA`'s fixed curve shape from `FREE`'s free-form one (how `min`/`max`/`value` combine to produce a per-stop shift) — that's engine work (`engine-ui-color-palette`), referenced here but not redefined; this spec covers the UI-facing contract (fields shown, persistence shape, migration) only.
- Any redesign of the existing flat-shift UX for `LINEAR` mode — explicitly required to stay identical to today.
- Exposing the curve concept anywhere beyond hue/chroma shift (e.g. lightness/easing already has its own, separate curve system documented in [Scale](scale.md) — not touched by this spec).
- The exact implementation of the local runtime-safe conversion (e.g. whether it caches its result or re-runs every load) and of the cloud SQL migration function (naming, whether it's a one-off script or a repeatable function) — mechanism is confirmed (see Rules), exact code is an implementation detail for whoever builds this.
- Redesigning the existing lightness-distribution easing system itself (curve icons, "Distribution easing" section, stop-position math) — confirmed distinct from the new velocity axis, not touched by this spec.
- Any change to [Settings](settings.md)'s existing `algorithmVersion`/"Chroma velocity" gamut-mapping control — confirmed to be an unrelated, separate mechanism that stays exactly as-is; not merged, renamed, or removed by this spec.
- The precise mechanical definition of the new velocity axis beyond "applies to lightness and to the hue/chroma shift" — genuinely unresolved, tracked in Open questions rather than specified here.

## Implementation notes

No implementation exists yet. What has to be built, concretely:

- **Engine (`engine-ui-color-palette`)**: `ShiftConfiguration`'s hue/chroma shape needs to grow from a bare number to `{ min, max, value, curve }`; the stop-by-stop shift-application logic needs to become curve-aware (flat passthrough for `LINEAR`, threshold interpolation through neutral at the midpoint for `HYPERBOLA`/`FREE`, differing only in the shape of that interpolation function).
- **UI — Scale module** (`src/ui/modules/scale`): the existing global hue/chroma sliders (see [Scale](scale.md) Rules — "global offsets applied to the whole scale") need the 3-way curve selector (`LINEAR`/`HYPERBOLA`/`FREE`, in that order), with the field layout varying by curve (one field for `LINEAR`, one mirrored field for `HYPERBOLA`, two independent `L`/`R` fields for `FREE` — see Rules) — note the current Figma mockup labels these `Min`/`Max` at the global level, which per the confirmed decision should become `L`/`R` copy to match the per-color panel (the underlying field names stay `min`/`max`). Additionally, the panel needs restructuring into clearer Lightness/Chroma/Hue sections, plus the **new velocity tabs** (a new, independent control — not sourced from Settings' `algorithmVersion`, see Rules) wired to affect both lightness and the global hue/chroma shift.
- **UI — Colors module** (`src/ui/contexts/Colors.tsx`): the existing per-color "more parameters" panel (see [Colors](colors.md) User flow step 3) needs the same curve selector plus the value-field ↔ `L`/`R`-field toggle shown in the Figma `Colors` frame's "parameters" panel — and Reset needs to clear the full new shape, not just a single value.
- **UI — Settings module** (`src/ui/modules/settings`): `algorithmVersion` (see [Settings](settings.md) User flow step 4 — documented there only as "algorithm version (v1/v2/v3)"; real UI label confirmed via Tolgee as **"Chroma velocity"**) is a **separate, unrelated gamut-mapping mechanism** (converges lightness+chroma onto the sRGB gamut) — confirmed to stay exactly as-is, not touched, merged, or removed by this spec. The new velocity axis introduced here is independent of it.
- **Bridges**: both `UPDATE_SCALE` (global shift, per [Scale](scale.md)) and `UPDATE_COLORS` (per-color shift, per [Colors](colors.md)) already carry hue/chroma shift as part of their existing full-payload messages — their payload shape needs to grow to the new `{min,max,value,curve}` object; no new message type is obviously needed, but worth confirming against the actual bridge code once this is picked up.
- **Local persistence — migration**: every stored local palette holds hue/chroma shift as a bare number today; confirmed direction is a **runtime conversion method** (not a versioned migration step) that runs whenever the plugin loads a palette, built to fail safe (no thrown exceptions) on already-migrated or malformed data, converting to `{ min, max, value, curve: 'LINEAR' }`.
- **Cloud persistence — migration**: confirmed direction is a **SQL function** run directly against the Supabase-backed palettes table, separate from and not dependent on the local runtime conversion — zero tolerance for data loss or read errors on existing published palettes.
- **Analytics**: [Scale](scale.md) already flags that hue/chroma shift changes aren't tracked at all today (confirmed gap in that spec); [Colors](colors.md) does track `SHIFT_HUE`/`SHIFT_CHROMA`/`RESET_HUE`/`RESET_CHROMA` per-color. Adding curve-mode and velocity tracking should piggyback on however those gaps get closed, rather than introducing a fourth, inconsistent tracking scheme — as its own, new event, since the velocity axis is confirmed independent of `algorithmVersion`'s existing (unaudited here) tracking.
- **Platforms**: shared core logic per the ticket ("Tous les éditeurs concernés") — no platform-specific branching expected, consistent with how [Scale](scale.md)/[Colors](colors.md) already work identically across Figma/Penpot/Sketch/Framer.

## Open questions

- **What the new velocity axis mechanically does isn't specified yet.** Confirmed to be independent of both existing candidates — not [Settings](settings.md)'s `algorithmVersion`/"Chroma velocity" (gamut-mapping across lightness+chroma) and not [Scale](scale.md)'s "Distribution easing" (lightness stop-position curve) — but what it actually computes when applied "to lightness" and "to the global hue/chroma shift" hasn't been defined. Needs a follow-up with the requester before engine work can start.
- **Value set for the velocity tabs is undecided**: since it's confirmed not to reuse `algorithmVersion`'s (`Linear`/`Sinusoidal`/`Sinusoidal and hyperbolic`) or lightness easing's (`Linear`/`Sine`/`Quad`/`Cubic`/`Ease in`/`Ease out`/`Ease in and out`) value sets as-is, the new control's own options need defining from scratch — blocks finalizing the Tolgee key decisions above.
- The precise mathematical interpolation function used between thresholds for `HYPERBOLA`/`FREE` (beyond the now-confirmed input mechanism — mirrored single value vs. two independent values) is engine implementation detail, tracked in Out of scope, not a spec-level open question.
