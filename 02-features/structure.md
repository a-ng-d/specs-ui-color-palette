- **Status**: Draft
- **Package(s) concerned**: `ui-ui-color-palette` (not implemented yet), `engine-ui-color-palette` (`System` class — already implemented, see below), `api-ui-color-palette` (`/get-color-system` — already implemented; two new persistence columns are needed, see Implementation notes), local & cloud persistence (**not implemented — see Implementation notes**)

- **Related spec**: [Color System (domain model)](../01-domain-model/color-system.md), [Color System (feature)](color-system.md), [Palette](../01-domain-model/palette.md) §6 (local/published lifecycle), [Actions](actions.md) (mode switcher), [Inspect](inspect.md), [Export](export.md)

- **Design**: Figma — `UICP Screens` file, node `4972:31593` ("Structure"), 3 sub-frames: `Taxonomy` (`4879:30216`), `Binding` (`4874:15680`), `Visualize` (`4879:30382`)

## Problem

[Color System (feature)](color-system.md) already scopes the semantic layer's engine/API/MCP behavior and flags that no design-tool UI exists yet. This spec names and scopes that UI concretely: **Structure**, a new top-level mode sitting in the mode switcher between Inspect and Export (`EDIT` / `INSPECT` / **`STRUCTURE`** / `EXPORT`). It lets a user define a taxonomy (semantic categories: Role, Prominence, State, Surface/Content, or a custom set of dimensions) and bind each taxonomy path to a primitive palette shade — turning `blue:500` into "brand default" — using the `System` module already implemented in `engine-ui-color-palette` (`src/modules/system/system.ts`).

The engine side is done: `System.makeSystemData()` resolves a taxonomy schema + bindings against a palette's themes/colors/shades into a token matrix (path × theme → shade or null), and `System.makeSystemLibraryData()` produces the flat list of per-platform library-object ids (`collectionId`/`modeId`/`variableId`/`styleId`/`catalogId`/`setId`/`tokenId`) needed to track what's already synced where. Nothing on the UI side reads or writes any of this today — no mode, no store, no bridge, and no persisted `system` field on a palette record anywhere (local document storage or the Supabase-backed remote). That's the gap this spec scopes.

## User flow

The mode reuses the app's existing chrome (same top bar: back button, palette name, "Published" chip) and adds its own left-hand sub-tab column with three tabs, matching the Figma frames: **Taxonomy**, **Binding**, **Visualize**.

1. From the mode switcher, the user opens **Structure** — a 4th segmented-control option, positioned between Inspect and Export (icon order in the mockup: sliders = Edit, eye = Inspect, list = **Structure**, `</>` = Export), gated like the other three (only shown if active for the current plan/platform).
2. The mode's own top-bar action is a single primary button, **"Sync with local variables"** — distinct from Edit's 3-way styles/variables/tokens sync menu; Structure syncs its own semantic collection/tokens on its own action (see Rules for what that sync creates per platform).
3. **Taxonomy tab** (first sub-tab, default on open): two columns.
   - Left, **"Groups (N)"** with a `+` to add a group: each group row (e.g. `Type`, `Surface`, `State` in the mockup) has a toggle/select control (to pick which group's members show on the right) and a `—` to remove the group.
   - Right, **"Members (N)"**: the members of the currently-selected group (e.g. for `Surface`: `Primary`, `Secondary`, `Neutral`, `Brand`, `Danger`, `On Brand`, `On Danger`), each renamable inline, each with its own `—` to remove, and a `+` to add a member.
   - **First open, no taxonomy yet**: a non-modifiable example taxonomy is pre-loaded so the screen is never empty on first use. The user has two actions available: reuse/duplicate the example (to get an editable copy) or **start from scratch** (a blank taxonomy) — not just delete.
   - **Confirmed example content** (simple, 3 groups): **Type** → `Background`, `Text`, `Icon`, `Border`; **Prominence** → `Primary`, `Secondary`, `Tertiary`, `Accent`, `Danger`, `Success`, `Warning`, `Info`; **State** → `Default`, `Hover`, `Pressed`, `Disabled`. This supersedes the illustrative group/member names shown in the current Figma mockup (`Type`/`Surface`/`State` with different members) — the mockup shows the layout, this list is the actual seed content to ship.
4. **Binding tab**: a searchable ("Search tokens…") flat list, grouped by header rows per resolved path prefix (e.g. `Background / Primary`), with one row per remaining dimension member (e.g. `Default`, `Hover`, `Pressed`, `Focus` — the State group). Each row has:
   - A dropdown to pick the primitive ref, shown as `<ColorName> / <stop>` (e.g. `Primary / 50`); unbound rows default to showing the palette's first/generic color (`UICP / <stop>` in the mockup) rather than a blank value.
   - A `···` menu opening a **Details** side panel: a `description` textarea ("What's it for?"), an **Excluded** checkbox, and a read-only **Values** section showing the resolved color per theme (e.g. `Light #6A4D00`, `Dark #937500`) — this is `SystemDataRef` resolved output, not itself editable here.
5. **Visualize tab**: a **read-only dependency diagram**, built with **React Flow** — its purpose is to let the user understand the structure at a glance (how taxonomy paths relate to and depend on the bound primitive shades), not a token-matrix table. **Proposed layout** (not yet mocked up in Figma — this is a structural proposal, pending an actual visual design pass):
   - **Two-column, left-to-right graph**, auto-laid-out (e.g. via `dagre`/`elkjs`, not manually positioned — the taxonomy is dynamic in size). Left column = **semantic nodes**, one per resolved taxonomy path (e.g. `Background / Primary / Default`), visually clustered by their first taxonomy group (`Type`, in the shipped example) using React Flow group/parent nodes. Right column = **primitive nodes**, one per distinct palette shade actually referenced, each showing a small color swatch + `<ColorName> / <stop>` label.
   - **Edges** run semantic → primitive: a solid edge, tinted with the primitive's own color, for a bound-and-resolved path. An unbound path connects to nothing (or a single shared "— Unbound —" placeholder node) rather than drawing a fake edge. An excluded path shows a visibly dimmed node with an "Excluded" badge and no edge at all — consistent with the confirmed engine behavior that excluded tokens never resolve to anything (see Rules).
   - **Theme-scoped**: reuses the same theme switcher already present elsewhere in this app's top bar (see [Preview](preview.md)) — edges reflect the selected theme's bindings only; switching theme re-renders which primitive node each semantic node's edge points to, rather than duplicating the whole graph per theme.
   - **Interaction stays read-only**: pan/zoom and hover-to-highlight-connected-edge are fine; clicking a semantic node could deep-link to that row in the Binding tab (navigating away, not editing in place) rather than opening any edit affordance directly inside Visualize.
   - This is a structural starting point for whoever designs the actual Figma frame, not a final layout — see Open questions.
6. Saving persists the taxonomy + bindings (`SystemConfiguration`) against the palette — locally at minimum, and to the cloud when the palette is published/synced (see Implementation notes: **not built today**).
7. On sync/export (Figma/Penpot/Sketch/Framer, and generated documentation), the semantic layer rides alongside primitives per the per-editor rules already scoped in the ticket (see Rules).

## Rules

- A taxonomy with zero groups is valid and produces zero tokens (not an error) — same rule as the domain model.
- A token with no binding still appears (shown against a default/generic color in the Binding tab, e.g. `UICP / <stop>`) rather than being dropped — a taxonomy can exist before every path is bound.
- A binding whose ref doesn't resolve for a given theme (e.g. a theme missing that color/shade) nulls only that theme's token, not the whole binding.
- **Exclusion — resolved, engine is the source of truth**: a binding can be marked `isExcluded` via the Binding tab's Details panel checkbox. The engine (`System.resolveToken()`) is authoritative: an excluded token resolves to a null `shadeId` for every theme (the same code path as "no binding exists") — so an excluded token **doesn't show up anywhere at all**: not in code, not in variables, not in tokens, not in any export, not in generated documentation. This confirms the engine's actual behavior as correct and **corrects** the earlier documented claim in [Color System (domain model)](../01-domain-model/color-system.md) and [Color System (feature)](color-system.md) that excluded tokens are "still fully resolved internally" — they are not; both docs have been updated accordingly. Practical consequence for Structure mode: the Binding tab's Details panel has nothing to show in its "Values" section for an excluded row (no per-theme value is ever computed), so that section should be hidden/empty when `Excluded` is checked, not just visually de-emphasized.
- **Example taxonomy**: shown pre-loaded and not directly editable in place; the user either reuses/duplicates it to get an editable copy, or starts a new taxonomy from scratch (blank). Two viable implementations, either is acceptable: an `isExample` flag, or simply synthesizing the example in the component's own state whenever the store's taxonomy is empty (no persisted flag at all until the user acts on it). **Reusing/duplicating the example only copies the schema (groups/members) — bindings always start empty and must be created by the user**; there is no pre-filled/suggested binding set. Content: `Type` (Background/Text/Icon/Border) × `Prominence` (Primary/Secondary/Tertiary/Accent/Danger/Success/Warning/Info) × `State` (Default/Hover/Pressed/Disabled) — see User flow.
- **Unbound taxonomy still syncs**: even with zero bindings, syncing to a platform's variables/styles creates the semantic structure (collection/tokens/styles), each entry resolved to a per-platform default color, rather than being skipped — confirmed by the requester.
- **Broken binding link**: if a binding's `ref` stops resolving (the referenced color/shade was removed or renamed from the palette), the user is **notified and prompted to rebind it** — not silently nulled and not blocking. Shown as a warning **IconChip** plus helper text on the affected row (not a toast). This resolves the equivalent open question inherited from [Color System (feature)](color-system.md).
- **Primitive/semantic reuse detection**: whether a primitive collection/variables/tokens already exist for this palette on a given platform (the "primitive check" phase below) is determined by **id linkage already tracked in `LibraryData`** (the existing primitive-sync tracking record); whether a semantic structure was already synced before (to update in place rather than duplicate on repeat syncs) is determined the same way via **`SystemLibraryData`** (`System.makeSystemLibraryData()`'s `collectionId`/`modeId`/`variableId`/`styleId`/`catalogId`/`setId`/`tokenId`). This is id-based, not name/heuristic-based.
- **Primitive rename trigger — confirmed**: the " - Primitive" suffix (Figma) / "Primitives" group (Penpot) is (re-)applied on **every sync**, not just the first time a semantic layer is introduced — a simple idempotent check each run, no extra state to track for "has this already been renamed."
- **Platform-side drift is a non-issue by construction**: because the semantic ↔ primitive link is by id (not by name/color/scope), a user renaming, recoloring, rescoping, or redescribing a primitive variable/token on the platform side **never breaks the semantic link**. If a linked primitive variable/token is missing entirely (deleted), it's simply re-added — confirmed by the requester as **the same reconciliation mechanism primitives already use today**, reused as-is; no new logic needed for this case. This is distinct from the in-app "broken binding link" rule above, which covers a different scenario: the user editing the taxonomy/bindings *inside* Structure mode itself (e.g. removing a color from the palette that a binding's `ref` pointed to) — that case is a Binding-tab UX concern (warning IconChip + rebind prompt), not a platform-sync concern.
- **Sync pipeline — resolved, restated precisely** (per platform): 1) **Run the existing primitive sync mechanism as-is** — whatever create-or-update flow primitives already go through today runs first, unchanged; this is what the earlier "primitive check" phase actually means, not a new detection step. 2) **Create the semantic structure and bind it** to whichever primitives resulted from step 1 (freshly created or just updated) — the semantic collection/token-set/style-folder shell is built, then filled with the resolved values (or per-platform default color for unbound paths), referencing those primitives. No separate "did the primitive collection change?" detection logic is needed — step 1 always runs, and step 2 always binds against its output.
- **Per-editor sync/export** (from the ticket, scoping the eventual bridge/export work — not built yet):
  - **Figma**: a new Variables collection dedicated to semantics, with variables referencing the primitive variables. If a primitive Variables collection already exists for this palette, it's reused and renamed with a **" - Primitive"** suffix to disambiguate it from the new semantic collection. Modes stay owned by primitives (simpler, supports arc/circular inversions already handled there). Styles: a "Primitives" folder **and** a "Semantics" folder generated per exported palette, both created even when semantics are empty.
  - **Penpot**: new Token Sets referencing the primitive sets; existing primitive tokens get moved/wrapped under a **"Primitives"** group to make room for the new semantic sets. Themes stay owned by the primitive sets. Styles: same primitive + semantic folder split as Figma, created even when empty.
  - **Sketch**: styles and variables only — no cross-referencing between variables/styles (platform constraint). Primitive + semantic folders are created even when empty, with **no aliasing/binding capability at all** — the semantic *role* is conveyed purely through the "Semantics" folder/naming, not through any live reference to the primitive value (confirmed generalization, see also [Color System (feature)](color-system.md)).
  - **Framer**: styles with an automatically generated inverted color. A "Primitives" and a "Semantics" folder are added inside the exported palette's folder, created even when semantics are empty — same no-aliasing constraint as Sketch; role via structure/naming only.
- **Generated documentation** (Figma/Penpot/Sketch/Framer — the four editors that support generated docs): a shared template gains a taxonomy breakdown table (path → bound color(s)). A semantic group with no bound color contributes no row, but the table structure stays present. Excluded bindings never appear in this table.
- The semantic layer is additive and non-destructive: building/editing it never mutates the underlying palette (`base`/`themes`), consistent with the domain model.
- **Local persistence**: the semantic layer is scoped **per local palette** — it's an additional parameter carried alongside a palette's existing local record, not a separate global object. It stores the **editable** shape (schema + bindings, i.e. `SystemConfiguration`), the same shape used by the cloud columns below — not the resolved `SystemData` — so there's nothing to reconcile when reopening a palette. Its JSON is **compressed** before being written to local storage — **LZ-based compression** (e.g. `lz-string`) is the confirmed direction for this local/document storage use case (exact library/timing left as an implementation detail, not a blocker).
- **Cloud persistence — resolved, two columns, not one**: the cloud palettes table needs **two new `jsonb` columns**, **`taxonomy`** (the schema — `TaxonomySchema`'s `groups`) and **`binding`** (the bindings array — `TaxonomyBinding[]`), rather than a single column holding resolved `SystemData`. This keeps cloud storage on **parametrization** (store exactly what the user configured, i.e. `SystemConfiguration`'s two parts) rather than storing a fully-resolved, derived projection — which removes the reconciliation problem entirely: reopening/pulling a palette from the cloud just reads `taxonomy` + `binding` back into the same editable shape the Binding tab already works with; nothing needs to be reverse-engineered from resolved output. When a palette is fetched via the cloud, both `taxonomy` and `binding` are retrieved together (as a pair, always) to reconstruct `SystemConfiguration`. Confirmed by the requester, replacing the earlier single-`structure`-column decision.

## Acceptance criteria

- [ ] Given a palette is open, when the user switches to the Structure mode, then they land on the Taxonomy tab and can create a taxonomy (add/rename/remove semantic groups and members).
- [ ] Given a taxonomy exists, when the user assigns a binding via the Binding tab's ref dropdown, then the primitive ↔ semantic binding is persisted via the existing engine contract (`SystemConfiguration`).
- [ ] Given Structure mode is opened for the first time on a palette with no taxonomy, then a non-editable example taxonomy is shown, and the user can either reuse/duplicate it or start a new one from scratch.
- [ ] Given a palette with no semantic layer defined, when it's opened normally (Edit/Inspect/Export), then there is no regression — behavior is identical to today.
- [ ] Given a binding, when the user marks it excluded (Details panel checkbox), then it never resolves to a value for any theme, and consequently never appears in generated code, generated documentation, or any platform export/variable/token — matching the engine's actual (now-confirmed-correct) behavior, not the earlier "still resolved internally" assumption.
- [ ] Given a taxonomy with unbound paths, when the user syncs to a platform, then the semantic structure (collection/tokens/styles) is still created, using a per-platform default color for the unbound entries, rather than being skipped — following the confirmed 2-step pipeline (run existing primitive sync → build & bind semantic structure against its output).
- [ ] Given the example taxonomy is used as-is or as a starting point, then it contains exactly `Type` (Background/Text/Icon/Border) × `Prominence` (Primary/Secondary/Tertiary/Accent/Danger/Success/Warning/Info) × `State` (Default/Hover/Pressed/Disabled).
- [ ] Given a binding whose `ref` no longer resolves (the referenced color/shade was removed or renamed), when the Binding tab renders that row, then a warning IconChip with helper text is shown, offering the user a way to rebind it — not silently nulled, not blocked.
- [ ] Given a local palette with a system defined, when it's saved, then the editable `SystemConfiguration` (schema + bindings) is persisted as an LZ-compressed JSON parameter on that palette's local record.
- [ ] Given a palette with a system defined is published/synced to the cloud, then its schema and bindings are persisted in the new `taxonomy` and `binding` `jsonb` columns respectively; pulling that palette back reconstructs the same editable `SystemConfiguration` from those two columns without any reconciliation step.
- [ ] Given the Visualize tab, then it presents a read-only dependency diagram of the taxonomy's structure (paths ↔ bound primitive shades) — **exact diagram layout still to be designed, see Open questions**.
- [ ] Given a platform sync, then reuse/idempotency of an existing primitive or semantic collection/tokens/styles is determined by id linkage already recorded in `LibraryData` (primitives) and `SystemLibraryData` (semantics), not by name-matching.
- [ ] Given a Figma sync, then a semantics-only Variables collection is created referencing primitive variables; an existing primitive collection is renamed with a " - Primitive" suffix rather than duplicated; both a "Primitives" and a "Semantics" styles folder are generated even when semantics are empty.
- [ ] Given a Penpot sync, then semantic Token Sets referencing primitive sets are created, existing primitive tokens are grouped under "Primitives", with the same always-present primitive/semantic folder split for styles.
- [ ] Given a Sketch export, then primitive and semantic style/variable folders are created even when empty, with no cross-referencing (platform constraint, by design).
- [ ] Given a Framer export, then "Primitives" and "Semantics" folders are added to the exported palette's folder, with an automatically generated inverted color in styles, even when semantics are empty.
- [ ] Given any of the four documentation-supporting editors, when documentation is generated, then it includes a taxonomy breakdown table (empty rows omitted, structure always present, excluded bindings never shown).

## Out of scope

- Any change to `System`/`makeSystemData`/`makeSystemLibraryData` in `engine-ui-color-palette` — the engine contract is implemented and considered stable input for this spec.
- The zip-export handling for multiple generated documents (flagged by the ticket as an engine-side evolution) — tracked separately, not a UI concern here.
- The Visualize tab's final visual design — confirmed to be a read-only dependency diagram of the taxonomy structure, but the Figma frame for it is currently empty (expected/normal at this stage per the requester); only Taxonomy and Binding are designed today.
- **Resolved** (was an open question in [Color System (feature)](color-system.md)): hand-editing is the confirmed v1 interaction — the dropdown ref picker and free-form group/member naming shown in the Figma mockup stay as-is; no orchestrator-style propose/refine/confirm flow. A lighter-weight, **future (non-v1)** enhancement is confirmed but not designed yet: once a color is picked for one binding, suggest an adjacent shade (darker/lighter, same color family) as a starting point for related bindings — out of scope for this spec's v1.

## Implementation notes

No implementation exists yet. What has to be built, concretely:

- **Mode plumbing**: `Mode` (`ui-ui-color-palette/src/types/app.ts:26`) is currently `'EDIT' | 'INSPECT' | 'EXPORT'` — needs a 4th value, `'STRUCTURE'` (confirmed as the literal shown in the Figma segmented control). `OpenPalette.tsx`'s `features()`/`modes` array and `render()` switch (one `case` per mode, each wrapped in a `Feature isActive` gate) need a 4th branch between `INSPECT` and `EXPORT`, rendering the new `StructurePalette`. `features.ts`'s `featuresScheme` needs a matching `STRUCTURE` entry. `Actions.tsx`'s tab-array construction (three conditionally-spread literals, order-significant) needs a 4th block inserted between the `INSPECT` and `EXPORT` blocks, plus its own top-bar variant (back button, read-only name, "Published" chip, the "Sync with local variables" primary button, mode switcher — no other sync/export actions, per the mockup).
- **Sub-tab plumbing**: `Context` (`app.ts`) has no entries for Taxonomy/Binding/Visualize yet (compare `'REPORT'`/`'PROPERTIES'` used by Inspect) — three new context ids are needed for these sub-tabs.
- **Stores**: no store exists for `SystemConfiguration`. `stores/palette.ts` (`$palette` deepMap) holds the current palette with no `system` key — a `$system` slice (schema + bindings) needs to be added there or as a sibling store, following the same nanostores pattern (`deepMap`), not Zustand.
- **Bridges**: none exist. `src/bridges/updates/` has `updateColors.ts`/`updatePalette.ts`/`updateScale.ts`/`updateSettings.ts`/`updateThemes.ts` — a new `updateSystem.ts` is needed (in both the shared web-bridges dir and every host platform's own `src/bridges/updates/`) for taxonomy CRUD and binding CRUD messages (e.g. `UPDATE_SYSTEM_SCHEMA`, `UPDATE_SYSTEM_BINDINGS`), following the same `UPDATE_*` message-and-handler pattern used elsewhere (`messages.ts`, per-host `loadUI.ts` dispatcher). Given this mode is a hand-editing, mutation-heavy surface (Taxonomy CRUD + Binding CRUD), it should be architected like `EditPalette` (multiple outbound `UPDATE_*` messages), not like `InspectPalette`'s near-read-only pattern.
- **Local persistence**: `FullConfiguration`/`ExchangeConfiguration` (`engine-ui-color-palette/src/types/configuration.types.ts`) and `PaletteData` (`data.types.ts`) all have no `system` field, and `stores/localPalettes.ts` has no notion of it either — a palette's taxonomy/bindings aren't part of the persisted local-document shape today, whether stored via `figma.currentPage.setSharedPluginData` (Figma host) or `window.localStorage` (web/dev bridges). Confirmed direction: add `system` (the editable `SystemConfiguration` — schema + bindings, **not** resolved `SystemData`) as an additional parameter **on the local palette record itself** (same `FullConfiguration`/local-document shape every other per-palette field lives on), **LZ-compressed** before storage given its potential size (one token per resolved path × per theme, though the stored shape itself — schema + bindings only — is smaller than the fully resolved matrix). Exact compression library (e.g. `lz-string`) and save timing (every edit vs. debounced) are implementation details left to whoever builds this, not a blocker.
- **Cloud persistence**: confirmed by the requester — **two new `jsonb` columns**, `taxonomy` and `binding`, need to be added to the palettes table on the Supabase side, holding `TaxonomySchema` and `TaxonomyBinding[]` respectively (`engine-ui-color-palette/src/types/system.types.ts`) — i.e. the editable `SystemConfiguration`'s two parts, stored separately, not the resolved `SystemData`. Today, `api-ui-color-palette/src/handlers/community.ts`'s publish/list/star handlers select/insert a fixed column list (`palette_id, name, description, preset, shift, colors, themes, color_space, algorithm_version, ...`) with no `taxonomy`/`binding` columns, and `/get-color-system` / `generate_code` (`handlers/palette.ts`) only ever accept `system` as a **stateless, request-scoped** input — nothing is stored server-side today. `PUBLISH_PALETTE`/`SYNC_PALETTE`/`PULL_PALETTE` need to be extended to read/write both columns together as a pair once they exist. Storing the raw, editable shape (rather than resolved `SystemData`) means there's no reconciliation logic needed when a palette is pulled back for editing.
- **Platform sync bridges**: none exist for the semantic layer on any platform — all four are new bridge work, layered on top of however primitives already sync (see [`03-platform-bridges/bridge-actions.md`](../03-platform-bridges/bridge-actions.md)), and should follow the confirmed 2-step pipeline per platform: (1) run the existing primitive create-or-update sync mechanism unchanged, (2) build the semantic collection/token-set/style-folder shell and bind it against whatever primitives resulted from step 1 — no separate detection/rename logic needed on top.
- **Analytics / Credits**: not specified yet by the ticket or by [Color System (feature)](color-system.md) — to define alongside the mode's build (likely a `trackStructureEvent` mirroring `trackExportEvent`/`trackActionEvent`, and a plan-gate on the mode itself the way Report/Properties are individually gated in Inspect).
- **Analytics / Credits**: not specified yet by the ticket or by [Color System (feature)](color-system.md) — to define alongside the mode's build (likely a `trackStructureEvent` mirroring `trackExportEvent`/`trackActionEvent`, and a plan-gate on the mode itself the way Report/Properties are individually gated in Inspect).
